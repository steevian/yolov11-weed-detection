# 毕设核心基线文档（basememory）

> 文档定位：本文件是毕业论文写作的核心文档，仅保留可直接支撑“系统设计、技术路线、实验结果、结论”章节的高价值信息,包括：核心计划、模型训练核心数据、模型对比分析结果、关键结论等核心信息。
> 维护说明：本文档只维护“论文主线核心事实与结论”。第一次实验过程中的过程流水、故障时间线、调试记录统一在 `docs/exp0.md` 维护，避免核心文档膨胀。第二次实验（老师要求的新实验）过程中的过程流水、故障时间线、调试记录统一在 `docs/exp1_log.md` 维护。

## 1. 项目名称与定位
- 仓库目录名：`yolo_web-main`
- README 标题：`yolov11-weed-detection`
- 系统形态：前后端分离的杂草检测系统（Vue3 + Flask + YOLO）
- 论文研究主线：在统一协议下完成 YOLOv11-S 基线与 MBV3/ECA/ECA2 改进模型的公平对比，验证轻量化与精度权衡。

## 2. 技术栈与系统边界
- 前端：Vue 3、Vite、TypeScript、Vue Router、Pinia、Element Plus、Axios、Socket.IO Client
- 后端：Python、Flask、Flask-Cors、Flask-SocketIO
- 模型推理：Ultralytics YOLO、PyTorch、OpenCV、NumPy、Pillow
- 数据与鉴权：SQLite、PyJWT
- 训练工程边界：训练代码集中在 `training/`，业务代码集中在 `yolo_weed_detection_flask/` 与 `yolo_weed_detection_vue/`，相互解耦。

## 3. 系统结构与已实现能力

### 3.1 核心目录
- `yolo_weed_detection_flask/`：后端服务入口、检测接口、数据与用户管理。
- `yolo_weed_detection_vue/`：前端页面、路由、接口封装。
- `training/`：训练脚本、模型配置、复现配置与守护脚本。
- `experiments/`：训练日志、评测结果、汇总报告、样例导出。

### 3.2 业务功能现状
- 检测能力：图像/视频/摄像头检测，含结果保存与进度推送。
- 历史记录：支持分页、筛选、详情查询与删除。
- 用户权限：JWT 鉴权，角色路由过滤。
- 训练管理：前后端接口已具备；业务后端以占位和 runs 扫描为主，不承担正式训练调度。

## 4. 环境与复现基线
- 机器：Windows 11，RTX 3060 Laptop GPU，16GB RAM。
- 项目训练环境：Miniconda `weedweb_detection`。
- 关键依赖：PyTorch GPU 版（`torch 2.9.1+cu128`）、Ultralytics `8.4.7`。
- 复现原则：关键实验前进行环境快照归档，保证可追溯。

## 5. 论文实验主线（以“11. 毕设训练与论文一体化执行基线”为分界后提纯）

### 5.1 总体实验原则
- 训练脚本与业务代码解耦。
- 实验产物统一沉淀到 `experiments/`。
- 三模型及扩展模型在同一评测协议下对比，保证公平性。

### 5.2 分阶段路线
- 阶段0：训练工程骨架与复现配置固化。
- 阶段1：数据集合并、划分、VOC->YOLO 转换、`data.yaml` 校验。
- 阶段2：YOLOv11-S 正式训练。
- 阶段3：YOLOv11-S-MBV3 训练。
- 阶段4：YOLOv11-S-MBV3-ECA/ECA2 训练。
- 阶段5：统一评测、样例导出、报告生成。

### 5.3 公平性关键约束
- 放弃历史 batch 混用结果，统一采用正式协议。
- 正式比较以统一参数执行：`epochs=200`、`batch=6`、`device=0`、固定数据协议。
- 早停判定：若所有模型遵循相同 patience 规则，早停属于公平训练规则内事件。

## 6. 数据与评测口径

### 6.1 数据划分与边界
- 训练/验证候选：`data2021 + data2022`。
- 测试集：`data2023`（独立年份）。
- 已确认：`data2023` 原始数据实际只覆盖 8 个类别，属于数据源客观约束。

### 6.2 结果解释边界
- 冒烟（50 epochs）仅用于流程验证，不用于论文最终结论。
- 论文主结论以 full200 与四模型统一评测结果为准。

## 7. 核心实验结果（论文可直接引用）

### 7.1 Full200 三模型统一评测（test, batch=1, imgsz=640）
- YOLOv11-S：mAP50=0.21548，mAP50-95=0.19114，FPS=56.28
- YOLOv11-S-MBV3：mAP50=0.24063，mAP50-95=0.21510，FPS=44.22
- YOLOv11-S-MBV3-ECA：mAP50=0.25014，mAP50-95=0.22382，FPS=43.35

### 7.2 四模型正式评测（含ECA2，test, batch=1, workers=0, imgsz=640）
- YOLOv11-S：P=0.3570，R=0.2657，mAP50=0.2155，mAP50-95=0.1911，FPS=57.35
- YOLOv11-S-MBV3：P=0.3962，R=0.2971，mAP50=0.2406，mAP50-95=0.2151，FPS=47.65
- YOLOv11-S-MBV3-ECA：P=0.3888，R=0.2974，mAP50=0.2501，mAP50-95=0.2238，FPS=39.48
- YOLOv11-S-MBV3-ECA2：P=0.4181，R=0.2835，mAP50=0.3450，mAP50-95=0.3229，FPS=45.27

### 7.3 ECA2 相对旧ECA增量
- ΔP=+0.0293
- ΔR=-0.0139
- ΔmAP50=+0.0949
- ΔmAP50-95=+0.0990
- ΔFPS=+5.78
- ΔParams=-1,847,246
- ΔFLOPs=-4,776,253,952

## 8. 核心分析结论（融合 analysis1 的高价值内容）
- 数据增强是开启且有效的；测试性能下降并非“未做增强”导致。
- 主要瓶颈是跨年份 domain shift：验证集高分与独立测试集低召回之间存在显著分布迁移。
- ECA2 已实现“更轻量 + 更高 mAP”的结构改进目标，但测试召回瓶颈仍未完全突破。
- 论文表达建议：将“公平消融结果”与“后续优化实验”分开展示，避免口径混淆。
